# 气球大乱踩 — 可行性分析报告

> FC《气球大战》(Balloon Fight) 移植鸿蒙 HarmonyOS NEXT 的技术方案与难点分析

## 一、原版游戏核心要素

### 1.1 基本信息
- **原版**: 1984 年任天堂街机 / 1985 年 FC，坂本育（Metroid 之父）设计，岩田聪（前任天堂社长）编程
- **灵感**: 源自 Williams 街机游戏 Joust（骑鸟飞行 + 从上方踩踏）
- **分辨率**: 256×240（NES 标准），精灵 16×16px

### 1.2 核心玩法

| 要素 | 说明 |
|------|------|
| 气球系统 | 背 2 只气球，可独立被戳破。2→浮力大，1→浮力减半，0→坠落死亡 |
| 攻击规则 | **只有从上方接触敌人才能戳破对方气球**，侧面/下方碰撞 = 自己被戳 |
| 屏幕环绕 | 飞出左边从右边出现，水平无限循环 |
| 平台着陆 | 着陆到中央平台后气球自动重新充气 |
| 复活机制 | 敌人落水后在平台重生带新气球，玩家死亡后屏幕中央重生 |

### 1.3 两种游戏模式

| 模式 | 玩法 |
|------|------|
| **Game A — Balloon Fight** | 消灭所有敌人过关，支持双人合作。敌人分绿/蓝/红三档难度 |
| **Game B — Balloon Trip** | 无尽滚动避障，自动向左滚屏，躲避闪电收集火花。标志性模式 |

### 1.4 物理系统（灵魂所在）

岩田聪编写的物理系统简洁但手感极佳：

```
每帧更新:
  velocity.y += gravity          // 恒定重力
  velocity.y = clamp(-INF, terminalVelocity)  // 终速限制
  position += velocity

拍打(Flap):
  velocity.y = flapImpulse       // 瞬时向上脉冲，不是持续推力

水平:
  velocity.x += horizontalAccel * input
  velocity.x *= friction         // 松手后有"飘"感
```

**关键参数（近似值）**:

| 参数 | 数值 | 说明 |
|------|------|------|
| 重力 | ~0.5-1.0 px/frame² | 每帧向下加速 |
| 拍打冲量 | ~-3.5 至 -4.0 px/frame | 瞬时向上速度 |
| 最大下落速度 | ~4.0-5.0 px/frame | 终速限制，防止无限加速 |
| 最大水平速度 | ~2.0-3.0 px/frame | 左右移动上限 |
| 水平阻力 | ~0.25-0.5 | 松手后减速系数 |

**手感好的原因**:
- 抛物线弧线自然 → "浮动感"
- 终速限制 → 即使下坠很久也能恢复，减少挫败感
- 拍打节奏感 → 找到合适的拍打频率保持高度
- 气球状态影响物理 → 2 气球终速低拍打好用，1 气球则困难

### 1.5 敌人系统

| 类型 | 行为 |
|------|------|
| 绿色气球人 | 温和，浮游模式 |
| 蓝色气球人 | 更快，主动追击 |
| 红色气球人 | 最激进，积极追击 |
| Blurp（鱼） | 水中游弋，跳出水面吞吃落水角色 |
| 螺旋桨 | 屏幕底部，产生上升气流 |
| 闪电云 | Balloon Trip 模式，固定路径移动 |
| Flipper（弹板） | 中央平台上的弹板敌人 |

### 1.6 得分系统

| 行为 | 分值 |
|------|------|
| 戳破空中敌人气球 | 500 分 |
| 戳破近地面敌人气球 | 750 分 |
| 连续击杀第 2 个 | 750 分 |
| 连续击杀第 3 个 | 1,000 分 |

**连杀递增**是高分策略的核心。

## 二、技术方案选型

### 2.1 三条技术路线对比

| 方案 | 渲染能力 | 开发难度 | 性能 | 维护成本 | 推荐度 |
|------|---------|---------|------|---------|--------|
| **A. ArkUI Canvas** | 2D 绘制 API，类似 HTML5 Canvas | 低（纯 ArkTS） | 60fps（< 100 精灵） | 低 | ⭐⭐⭐⭐⭐ |
| B. XComponent + OpenGL ES | GPU 加速 2D/3D | 高（需要 C/C++ NDK） | 极高 | 高 | ⭐⭐ |
| C. Cocos Creator 引擎 | 完整 2D/3D 引擎 | 中（引擎学习成本） | 高 | 中 | ⭐⭐⭐ |

### 2.2 推荐方案：ArkUI Canvas

**理由**:
1. Balloon Fight 是极简像素游戏，同屏精灵 < 30 个，Canvas 完全够用
2. 纯 ArkTS 开发，与 HarmonyOS 原生 API 无缝集成
3. `requestAnimationFrame` 提供 VSync 同步的游戏循环
4. Canvas API（`drawImage`, `arc`, `fillRect`）覆盖所有绘制需求
5. 触摸/手势 API 直接对接玩家输入
6. 不引入外部引擎，降低包体积和维护成本

## 三、核心技术难点与解决方案

### 难点 1：游戏循环与帧率控制

**问题**: ArkUI 的 Canvas 是声明式 UI 框架中的即时模式绘制，不像游戏引擎有原生 game loop。

**方案**:
```
Canvas 组件 → onReady 回调中启动游戏循环
游戏循环 = requestAnimationFrame(callback)
  → callback 中执行: 输入处理 → 物理更新 → 碰撞检测 → 渲染
  → 每帧预算 16.67ms（60fps）
```

**关键点**:
- 使用 `OffscreenCanvas` 在 Worker 线程做渲染计算，避免阻塞 UI 线程
- 脏矩形追踪：只重绘变化区域，不全屏刷新
- 静态元素（背景、平台）预渲染到离屏 Canvas，只绘制一次

### 难点 2：物理系统复刻

**问题**: 原版物理参数是基于 60fps NES 硬件的 sub-pixel 精度累加器，需要在不同刷新率设备上保持一致手感。

**方案**:
```typescript
// 核心物理模型（delta time 驱动，适配不同帧率）
interface PhysicsConfig {
  gravity: number           // 重力加速度 (px/s²)
  flapImpulse: number       // 拍打冲量 (px/s)
  terminalVelocity: number  // 终速 (px/s)
  horizontalAccel: number   // 水平加速度 (px/s²)
  horizontalMaxSpeed: number // 水平最大速度 (px/s)
  horizontalFriction: number // 水平阻力系数
}

// 每帧更新（deltaTime 秒）
function update(entity: Entity, dt: number) {
  // 重力
  entity.vy += config.gravity * dt
  entity.vy = Math.min(entity.vy, config.terminalVelocity)

  // 水平
  entity.vx += inputDirection * config.horizontalAccel * dt
  entity.vx *= Math.pow(1 - config.horizontalFriction, dt * 60)
  entity.vx = clamp(entity.vx, -config.horizontalMaxSpeed, config.horizontalMaxSpeed)

  // 位置
  entity.x += entity.vx * dt
  entity.y += entity.vy * dt

  // 屏幕环绕
  if (entity.x < -entity.width) entity.x = screenWidth
  if (entity.x > screenWidth) entity.x = -entity.width
}
```

**调参要点**:
- 先用原始 NES 参数（60fps 基准）在模拟器上跑通
- 在真机上用 deltaTime 归一化，确保不同帧率下手感一致
- 重点调：重力/冲量比值、终速、水平飘移感

### 难点 3：碰撞检测

**问题**: 需要实现"从上方踩踏"的精确判定，区分攻击方和被攻击方。

**方案**:
```typescript
// 碰撞检测：谁踩谁？
function checkCollision(a: Entity, b: Entity): CollisionResult {
  if (!boundingBoxOverlap(a, b)) return null

  // 关键：比较垂直速度和相对位置
  const aFromAbove = (a.vy > 0) && (a.y < b.y)   // A 在 B 上方且向下运动
  const bFromAbove = (b.vy > 0) && (b.y < a.y)   // B 在 A 上方且向下运动

  if (aFromAbove && !bFromAbove) return { attacker: a, victim: b }
  if (bFromAbove && !aFromAbove) return { attacker: b, victim: a }
  if (aFromAbove && bFromAbove)  return { attacker: null }  // 双方都踩，同归于尽
  return { attacker: null, mutual: true }  // 侧面碰撞，双方各损一气球
}
```

**判定规则优先级**:
1. 垂直位置 + 速度方向 → 谁在上面
2. A 的底部 vs B 的顶部 → 碰撞区域重叠
3. 同时踩踏 → 双方各损一气球

### 难点 4：敌人 AI

**问题**: 原版有三种难度的敌人 AI，需要复刻但不需要完全一致。

**方案**（简化版分层 AI）:
```typescript
interface EnemyAI {
  state: 'patrol' | 'chase' | 'retreat'
  aggroRange: number      // 视野范围
  reactionDelay: number    // 反应延迟（帧数）
  flapProbability: number  // 每帧拍打概率
}

// AI 行为状态机
function updateAI(enemy: Enemy, player: Entity, dt: number) {
  const dist = distance(enemy, player)

  switch (enemy.ai.state) {
    case 'patrol':
      // 随机左右飘浮 + 偶尔拍打
      if (dist < enemy.ai.aggroRange) enemy.ai.state = 'chase'
      break
    case 'chase':
      // 向玩家方向移动，尝试从上方接近
      enemy.targetX = player.x
      if (player.y < enemy.y - 20) {
        // 玩家在上方，尝试追上去
        enemy.flapTimer -= dt
        if (enemy.flapTimer <= 0) {
          flap(enemy)
          enemy.flapTimer = 0.3 + Math.random() * 0.2  // 随机拍打间隔
        }
      }
      break
    case 'retreat':
      // 气球被戳破一只后，下落同时变得更凶猛
      break
  }
}
```

### 难点 5：精灵动画与像素风格

**问题**: 如何在高分辨率屏幕上保持像素风格的同时让画面清晰。

**方案**:
```typescript
// 像素风格渲染策略
// 1. 使用 ImageSmoothingQuality 关闭抗锯齿
ctx.imageSmoothingEnabled = false

// 2. 逻辑分辨率固定（如 480×360），通过 scale 适配屏幕
const GAME_WIDTH = 480
const GAME_HEIGHT = 360
const scale = Math.min(screenWidth / GAME_WIDTH, screenHeight / GAME_HEIGHT)
ctx.scale(scale, scale)

// 3. 精灵图绘制
// 原版角色 16×16px，放大到逻辑坐标的 24×24 或 32×32
ctx.drawImage(spriteSheet, srcX, srcY, 16, 16, x, y, 32, 32)
```

**美术方案**:
- 用 **像素风** 美术风格（致敬原版），分辨率约 480×360 逻辑坐标
- 角色精灵图 (Sprite Sheet)：拍打动画 2-3 帧、气球状态变化、坠落动画
- 背景层：深色天空 + 星星 + 云朵平台
- 水面层：蓝色波浪 + 鱼的游动动画

### 难点 6：音效系统

**问题**: 游戏需要多种音效同时播放（拍打、气球爆炸、落水、BGM）。

**方案**:
```
音效 → SoundPool（低延迟，支持并发）
  - 拍打声: flap.mp3
  - 气球爆炸: pop.mp3
  - 落水声: splash.mp3
  - 连击音: combo.mp3

BGM → AVPlayer（单实例循环播放）
  - Balloon Fight BGM
  - Balloon Trip BGM
```

### 难点 7：触摸操作适配

**问题**: 原版是手柄操控（方向键 + A/B），移植到触摸屏需要重新设计。

**方案**:

| 操作 | 手柄映射 | 触摸方案 |
|------|---------|---------|
| 左右移动 | 方向键左/右 | **屏幕左半区域左右滑动** 或 **倾斜手机（陀螺仪）** |
| 拍打 | A 键 | **点击屏幕右半区域** 或 **任意位置点击** |
| 暂停 | Start | 顶部暂停按钮 |

**推荐交互方案**:
```
方案 A（简单）: 点击 = 拍打，左右滑动 = 移动
方案 B（经典）: 虚拟摇杆（左） + 跳跃按钮（右）
方案 C（创新）: 点击 = 拍打（朝点击方向水平移动），双指 = 暂停
```

## 六、风险与挑战

| 风险 | 严重度 | 应对 |
|------|--------|------|
| Canvas 渲染性能不足 | 低 | 30 个精灵同屏，Canvas 绰绰有余。极端情况用脏矩形 |
| 物理手感不好 | **高** | 多花时间调参，在真机上反复测试，参考原版参数 |
| 触摸操作不如手柄 | **高** | 设计多种操控方案让玩家选择，考虑支持蓝牙手柄 |
| 像素美术成本 | 中 | 用免费像素素材或 AI 生成，先占位后替换 |
| 鸿蒙 API 不熟悉 | 中 | Canvas API 与 HTML5 Canvas 高度相似，学习成本低 |

## 七、总结

**可行性：✅ 高**

FC 气球大战是一款**极简但精妙**的游戏，其核心是物理手感和"从上方踩踏"的规则。技术上完全可以用 ArkUI Canvas 在鸿蒙上复刻，不需要游戏引擎。

**最大的挑战不在技术，而在手感调参和操作适配。** 物理参数的微调决定了游戏是否"好玩"，触摸操作的舒适度决定了玩家是否愿意玩下去。

建议先做一个最小原型（Phase 1+2），在真机上验证物理手感和操作体验，再决定是否投入后续开发。
